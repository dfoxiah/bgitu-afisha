# Сценарий устной защиты проекта `bgitu-afisha` (10–12 минут)

## 1. Цель выступления
Показать, что проект не просто работает, а технически зрелый: архитектурно разделён, контролируем по качеству, легко расширяется и безопасен к изменениям.

## 2. Тайминг выступления
1. 0:00–1:00 — проблема и цель проекта.
2. 1:00–2:30 — бизнес-ценность и роли пользователей.
3. 2:30–5:00 — архитектура и ключевые модули.
4. 5:00–7:00 — стек и почему он выбран.
5. 7:00–9:00 — что улучшено в рефакторинге.
6. 9:00–10:30 — тестирование и quality gates.
7. 10:30–12:00 — выводы, масштабирование и ответы на вопросы.

## 3. Готовый текст для начала (1 минута)
«Здравствуйте, тема моей работы — платформа `bgitu-afisha` для управления университетскими мероприятиями.  
Система поддерживает три роли: студент, преподаватель и администратор.  
В рамках проекта я не только реализовал пользовательские сценарии, но и выполнил архитектурную ревизию: разделил ответственность между слоями, усилил типизацию, ввёл единый формат валидации и ошибок, добавил тестовый контур и техническую документацию для сопровождения.»

## 4. Что говорить по архитектуре (2.5 минуты)
1. «Слой `src/app/api/**/route.ts` — это thin controllers: они делают только авторизацию, валидацию входа и делегирование в сервисы.»
2. «Слой `src/server/**` содержит доменную логику. Там находятся сервисы для событий, профиля, админки, импорта и общих helper-функций.»
3. «Клиентский слой разделён на `src/features/**` (API-адаптеры и фичи) и `src/contexts/**` (оркестрация состояния).»
4. «Типы разнесены по назначениям: `domain`, `dto`, `api-contracts`, что снижает связанность и упрощает поддержку.»
5. «Такое разделение даёт предсказуемый путь запроса: `UI -> feature adapter -> API route -> server service -> Prisma`.»

## 5. Что говорить по стеку и его плюсам (2 минуты)
1. `Next.js`: единый fullstack-контур, гибрид SSR/CSR, удобный App Router и route handlers.
2. `React`: компонентность и скорость разработки UI, плюс `useOptimistic` для отзывчивого UX.
3. `TypeScript`: строгие контракты и безопасный рефакторинг без скрытых регрессий.
4. `Prisma + PostgreSQL`: type-safe работа с реляционной моделью и транзакционная надёжность.
5. `next-auth`: готовая аутентификация и role-based доступ.
6. `Tailwind CSS`: быстрый и консистентный UI без лишнего CSS-шаблонного кода.
7. `Zod`: schema-first валидация входных данных и единый источник правды для API.
8. `ESLint + smoke`: контроль качества перед финализацией и релизом.

## 6. Что говорить по рефакторингу (2 минуты)
1. «Монолитные API-маршруты событий декомпозированы: orchestration вынесена в `src/server/events/event-mutation-service.ts`, а контроллеры стали тонкими.»
2. «Добавлен schema-first слой валидации: `src/server/shared/schemas/*`, подключённый к ключевым endpoint.»
3. «Введены framework-фичи производительности: server cache tags, `next/image`, оптимистичные обновления.»
4. «Проведена нормализация типизации и устранены небезопасные участки.»
5. «Добавлены системные file-header комментарии по всем исходникам `src/**` для быстрой навигации команды.»

## 7. Что показать в демо (2 минуты)
1. Логин под студентом -> `/dashboard` -> `/events` -> регистрация на событие.
2. Логин под преподавателем/админом -> модерация участников -> отправка уведомления.
3. Профиль: изменение данных и сохранение.
4. Админ-панель: пользователи, события, импорт, логи.

## 8. Что сказать про тесты и качество (1.5 минуты)
1. «В проекте встроены обязательные quality gates: `lint`, `type-check`, `build`.»
2. «Есть smoke-контур: `tests/smoke/api-smoke.ts`, `tests/smoke/e2e-smoke.ts`, оркестратор `run-local.ts`.»
3. «Перед финализацией прогоняется `npm run test:smoke:local`, что покрывает критические маршруты и UI-потоки.»
4. «Это снижает риск регрессий при дальнейшем развитии системы.»

## 9. Финальная формулировка (30–40 секунд)
«Итог: проект приведён к поддерживаемой архитектуре, где бизнес-логика отделена от HTTP-слоя, валидация и типы унифицированы, а качество контролируется автоматизированными проверками.  
Система готова к развитию: можно безопасно добавлять новые роли, типы событий, интеграции и отчётность без переписывания ядра.»

## 10. Типовые вопросы комиссии и короткие ответы
1. Почему выбран именно этот стек?
Ответ: он даёт единый fullstack-процесс разработки, строгую типизацию и быстрый цикл поставки без потери качества.

2. Где обеспечивается безопасность доступа?
Ответ: в `next-auth` + role guards в `src/server/shared/session.ts` и проверках в route handlers.

3. Как предотвращаются регрессии?
Ответ: через обязательные quality gates (`lint`, `type-check`, `build`) и smoke-наборы API/e2e.

4. Что было самым критичным в рефакторинге?
Ответ: разделение монолитных обработчиков на thin controllers и доменные сервисы с единым форматом ошибок и валидации.

5. Какой главный технический результат?
Ответ: предсказуемая, расширяемая архитектура с прозрачными контрактами и сниженной сложностью изменений.

## 13. Что подчеркнуть как инженерные плюсы стека на защите
1. `Next.js`: в одном проекте и UI, и API — проще сопровождать и выпускать фичи.
2. `React`: быстрые интерактивные экраны и удобная декомпозиция на переиспользуемые компоненты.
3. `TypeScript`: строгие контракты между слоями, безопасный рефакторинг и меньше регрессий.
4. `Prisma + PostgreSQL`: надёжная реляционная модель и предсказуемые запросы к данным.
5. `next-auth`: централизованный контроль сессий и ролей для защищённых endpoint.
6. `Tailwind`: быстрая адаптивная вёрстка и единый визуальный стандарт.
7. `Zod`: schema-first валидация на входе API и единые правила обработки ошибок.
