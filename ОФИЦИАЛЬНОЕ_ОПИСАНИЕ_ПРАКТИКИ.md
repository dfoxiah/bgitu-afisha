## ВВЕДЕНИЕ И АКТУАЛЬНОСТЬ ПРОЕКТА

### Проблематика

В современных крупных образовательных организациях, таких как БГИТУ, организация и управление мероприятиями представляет собой комплексную задачу, требующую координации множества участников: студентов, преподавателей, администраторов, кураторов групп и органов студенческого самоуправления. Традиционные методы информирования о событиях (объявления на досках, рассылка по электронной почте, публикации в социальных сетях) демонстрируют ряд критических недостатков:

1. **Разобщенность информации**: События размещаются в различных системах и платформах (сайт БГИТУ, группы ВКонтакте, Telegram-каналы, рассылки), что приводит к дублированию и противоречивости информации. Студенты зачастую обнаруживают информацию о значимых событиях постфактум.

2. **Низкая персонализация**: Современные студенты ожидают, что информация будет приходить в соответствии с их интересами. Отправка одинаковых уведомлений всем без разделения по видам деятельности (спорт, культура, научные конференции) снижает отклик и увеличивает информационный шум.

3. **Недостаток аналитики**: Администрация университета не располагает оперативными данными о посещаемости и популярности мероприятий, что затрудняет принятие обоснованных решений о развитии внеучебной деятельности.

4. **Неэффективность управления**: Отсутствие централизованной системы затрудняет взаимодействие между различными структурными подразделениями БГИТУ (деканатами, центром культуры и спорта, студенческим советом), ведущее к дублированию функций и потере оперативности.

5. **Слабая обратная связь**: У студентов отсутствует удобный канал для подачи заявок на участие в мероприятиях, предложения новых идей и сообщения о проблемах.

### Актуальность решения

В условиях цифровизации образования создание единой платформы для управления событиями и их популяризации является не просто удобством, но стратегической необходимостью. Такая система позволит:

- **Повысить вовлеченность студентов** в научно-практическую и культурно-спортивную деятельность
- **Оптимизировать процессы планирования** мероприятий в рамках разных структурных подразделений
- **Обеспечить полную информационную прозрачность** о событиях университета
- **Собрать ценные данные аналитики** для совершенствования внеучебной деятельности

Целевая аудитория системы достаточно велика: по состоянию на 2024 год БГИТУ насчитывает более 5 000 студентов очной формы обучения, плюс примерно 1 500 преподавателей и сотрудников административного аппарата.

## 1. ИНДИВИДУАЛЬНОЕ ЗАДАНИЕ. РАЗРАБОТКА WEB-ПРИЛОЖЕНИЯ ДЛЯ УПРАВЛЕНИЯ МЕРОПРИЯТИЯМИ И СОБЫТИЯМИ УНИВЕРСИТЕТА

### 1.1 Постановка задачи и цели проекта

В ходе прохождения производственной (преддипломной) практики было получено индивидуальное задание на проектирование и разработку современной информационной системы — web-приложения «БГИТУ Афиша», предназначенного для централизованного управления событиями, мероприятиями и внеучебной деятельностью университета.

#### Основная цель проекта

Создание инновационной цифровой платформы, которая обеспечит:
- Централизованное размещение и продвижение всех значимых событий и мероприятий БГИТУ
- Удобную регистрацию студентов и отслеживание их участия
- Полную аналитику по посещаемости и популярности событий
- Организацию взаимодействия между различными структурными подразделениями университета

#### Задачи, решаемые в рамках проекта

1. **Аналитическая часть**: Проведение системного анализа текущих процессов организации мероприятий в университете, выявление узких мест и разработка целевой модели в нотации BPMN (Business Process Model and Notation). Описание сценариев использования в нотации UML Use Case.

2. **Проектирование архитектуры**: Разработка логической архитектуры системы на основе microservices-принципов и REST API. Выбор оптимального технологического стека для обеспечения масштабируемости, производительности и надежности.

3. **Проектирование базы данных**: Разработка логической и физической схем реляционной БД (PostgreSQL), включающей сущности: Событие, Участник, Категория, Регистрация, Уведомление и другие. Нормализация схемы до третьей нормальной формы.

4. **Разработка серверной части (Backend)**: Реализация REST API на фреймворке NestJS с реализацией:
   - Системы аутентификации и авторизации (JWT)
   - Ролевой модели доступа (RBAC: администратор, куратор события, студент)
   - Бизнес-логики управления событиями и регистрацией
   - Модуля аналитики для сбора и обработки данных о посещаемости
   - Системы уведомлений (в т.ч. интеграция с ВКонтакте и Email)

5. **Разработка клиентской части (Frontend)**: Создание отзывчивого (responsive) интерфейса на базе React, обеспечивающего удобство работы как со стационарных ПК, так и с мобильных устройств. Реализация следующих основных компонентов:
   - Каталога событий с фильтрацией и поиском
   - Страницы регистрации на событие
   - Личного кабинета студента с историей участия
   - Админ-панели для управления событиями и аналитики
   - Системы уведомлений в реальном времени

6. **Интеграция внешних сервисов**: Интеграция с платформой ВКонтакте (VK OAuth 2.0) для аутентификации и отправки уведомлений. Возможность импорта данных о студентах и структуре факультетов.

7. **Тестирование и оптимизация**: Проведение модульного (unit), интеграционного и функционального тестирования. Нагрузочное тестирование при одновременной работе нескольких тысяч пользователей. Оптимизация производительности.

8. **Развертывание (DevOps)**: Подготовка приложения к production-развертыванию с использованием контейнеризации (Docker) и оркестрации (Docker Compose).

#### Ожидаемый результат

Работоспособный прототип web-приложения, полностью готовый к опытной эксплуатации в среде БГИТУ, способный:
- Обслуживать одновременно несколько тысяч активных пользователей
- Обеспечивать отправку уведомлений в режиме реального времени
- Предоставлять администрации детальную аналитику по всем аспектам внеучебной деятельности
- Полностью заменить ручное управление событиями и регистрацией участников

### 1.2 Анализ предметной области и требований к системе

#### Исследование текущего состояния

Анализ предметной области был проведен путем изучения текущих процессов организации мероприятий в БГИТУ. Выявлено, что на сегодняшний день управление событиями осуществляется следующим образом:

**Участники процесса:**
- **Администрация**: Ректор, проректоры — принимают стратегические решения об организации масштабных событий
- **Центр культуры и спорта**: Организует спортивные мероприятия, концерты, фестивали
- **Деканаты факультетов**: Ответственны за факультетские события, олимпиады, конференции
- **Кураторы групп**: Информируют студентов о событиях, контролируют явку
- **Студенческий совет**: Организует внутригруппевые события
- **Студенты**: Целевая аудитория, участники событий

**Текущие болевые точки:**
1. Информирование осуществляется через несинхронизированные каналы (рассылки, соцсети, досок объявлений)
2. Нет централизованного учета регистраций студентов на события
3. Отсутствуют данные о реальной посещаемости (если событие прошло, никто не проверяет, сколько людей фактически пришло)
4. Невозможно быстро проанализировать популярность того или иного вида мероприятий
5. Сложность коммуникации между организаторами из разных подразделений

#### Обзор аналогичных систем

В ходе маркетингового анализа были рассмотрены следующие решения:

**1. Таких (Ticketmaster для образовательных организаций):**
- Преимущества: Мощная система продажи билетов, интеграция с платежами, масштабность
- Недостатки: Переусложнена для нужд университета, не учитывает специфику структуры БГИТУ, высокая стоимость

**2. Eventbrite:**
- Преимущества: Простой интерфейс, встроенная аналитика
- Недостатки: Англоязычный интерфейс, неудобен для внутренних университетских событий, часто взимает комиссии

**3. MyEvents (российское решение для ВУЗов):**
- Преимущества: Локализирован, имеет функции учета посещаемости
- Недостатки: Сложная интеграция, требует собственного серверного оборудования, высокая стоимость лицензии

**Вывод:** Проанализированные решения либо переусложнены, либо недостаточно адаптированы под специфику российского образовательного учреждения. Таким образом, разработка собственного решения является оправданной.

#### Функциональные требования

На основе анализа предметной области определены следующие функциональные требования:

##### Модуль каталога событий:
- Размещение информации о событиях (название, описание, дата, время, место, капацитет)
- Классификация событий по категориям (спорт, культура, образование, добровольчество и т.д.)
- Загрузка фотографий и медиаконтента для события
- Указание контактного лица/ответственного за событие
- Пометка события как «публичное» или «только для определенной группы»

##### Модуль регистрации и участия:
- Регистрация студента на событие с учетом капацитета
- Отмена регистрации и переработка свободных мест
- Экспорт списка зарегистрированных участников (для организаторов)
- Отметка явки при физическом присутствии на событии (с помощью QR-кода или ручной отметки)

##### Модуль уведомлений:
- Отправка уведомлений о новых событиях в избранных категориях
- Уведомления об изменении деталей события (перенос, отмена)
- Напоминания перед началом события (за 1 день, за 1 час)
- Интеграция с ВКонтакте и Email-рассылкой
- Управление подписками пользователем

##### Модуль аналитики:
- Информационный дашборд для администраторов
- График популярности мероприятий
- Аналитика посещаемости в разрезе категорий, факультетов, студенческих групп
- Экспорт отчетов в формате Excel/PDF
- Расчет KPI (средняя посещаемость, охват студентов, процент явки зарегистрированных)

##### Модуль управления (для кураторов и администраторов):
- Создание, редактирование и удаление событий
- Управление доступом к событию (кто может зарегистрироваться)
- Рассылка специальных уведомлений участникам события
- Модерирование комментариев и вопросов студентов

#### Нефункциональные требования

- **Производительность**: Система должна обслуживать одновременно до 10 000 активных пользователей без деградации качества обслуживания. Время ответа API — не более 200 мс.

- **Масштабируемость**: Архитектура должна позволять горизонтальное масштабирование (добавление новых серверов) без изменения кода приложения.

- **Безопасность**: Использование HTTPS, JWT-токены с ограниченным временем жизни, хеширование паролей, защита от XSS и SQL-инъекций, модуль аудита.

- **Доступность**: Система должна быть доступна 99.9% времени (не более 43 минут простоя в месяц). Использование redundancy и backup.

- **Адаптивность**: Интерфейс должен корректно отображаться на экранах от 320 px (смартфоны) до 4K (мониторы). Поддержка как desktop, так и мобильных браузеров.

- **Интегрируемость**: Система должна предоставлять REST API для возможной интеграции с другими сервисами БГИТУ (например, с личным кабинетом студента, системой расписания).

#### Анализ ролевой модели

В соответствии с ТЗ, система должна поддерживать следующие роли с разным уровнем доступа:

| Роль | Возможности | Ограничения |
|------|------------|------------|
| **Администратор** | Полный контроль: создание/редактирование/удаление событий, управление пользователями, просмотр всей аналитики, модерирование | Отсутствуют |
| **Куратор события** | Создание и редактирование своих событий, просмотр списков участников, отправка уведомлений, просмотр аналитики по своим событиям | Не может редактировать события других кураторов, не видит полную аналитику системы |
| **Куратор группы** | Просмотр участия студентов группы в событиях, информирование о внутригруппевых событиях | Не может создавать масштабные события, видит только данные своей группы |
| **Студент** | Просмотр каталога событий, регистрация и отмена регистрации, просмотр своей истории участия, подписка на уведомления | Не может редактировать события, видит только публичные события или события для своей группы |
| **Родитель** | Просмотр участия ребенка в событиях, получение уведомлений (опционально) | Ограниченный доступ, только информационный |

#### Бизнес-логика предметной области

Основной бизнес-процесс системы можно описать следующим образом:

1. **Этап планирования**: Куратор события создает карточку мероприятия (название, дата, место, категория, капацитет)
2. **Этап информирования**: Система автоматически отправляет уведомления заинтересованным студентам в зависимости от их подписок на категории
3. **Этап регистрации**: Студенты регистрируются на событие через интерфейс; система отслеживает количество свободных мест
4. **Этап реализации**: В день события студенты отмечаются как явившиеся (вручную или через QR-код)
5. **Этап аналитики**: Администрация анализирует данные о посещаемости и популярности для улучшения программы событий

### 1.3 Архитектура разрабатываемого приложения

#### Общая структурная схема системы

Архитектура приложения строится на основе модели **Decoupled Architecture** (развязанная архитектура), где клиентская часть (Frontend) и серверная часть (Backend) являются независимыми приложениями, взаимодействующими через стандартизированный REST API.

```
┌─────────────────────────────────────────────────────────────┐
│                    СЛОЙ ПРЕДСТАВЛЕНИЯ (UI)                  │
│  React SPA (Single Page Application)                         │
│  ├─ Каталог событий                                          │
│  ├─ Личный кабинет студента                                 │
│  ├─ Админ-панель                                            │
│  └─ Система уведомлений                                      │
└───────────────────┬─────────────────────────────────────────┘
                    │ HTTP/REST API
                    │ JSON
┌───────────────────▼─────────────────────────────────────────┐
│         СЛОЙ БИЗНЕС-ЛОГИКИ И УПРАВЛЕНИЯ (Backend)          │
│  NestJS Framework                                            │
│  ├─ Auth Module (JWT, OAuth VK)                              │
│  ├─ Events Module (CRUD операции)                            │
│  ├─ Registrations Module (регистрация участников)            │
│  ├─ Notifications Module (рассылка уведомлений)              │
│  ├─ Analytics Module (аналитика посещаемости)                │
│  └─ Users Module (управление пользователями)                 │
└───────────────────┬─────────────────────────────────────────┘
                    │ TypeORM / Prisma
                    │ SQL
┌───────────────────▼─────────────────────────────────────────┐
│           СЛОЙ ДОСТУПА К ДАННЫМ (ORM)                       │
│  Prisma ORM                                                  │
│  └─ Автоматическое преобразование запросов в SQL            │
└───────────────────┬─────────────────────────────────────────┘
                    │
┌───────────────────▼─────────────────────────────────────────┐
│           СЛОЙ ХРАНЕНИЯ ДАННЫХ (Database)                   │
│  PostgreSQL                                                  │
│  ├─ Таблица Events                                           │
│  ├─ Таблица Users                                            │
│  ├─ Таблица EventRegistrations                               │
│  ├─ Таблица Notifications                                    │
│  ├─ Таблица EventCategories                                  │
│  └─ Таблица AuditLogs                                        │
└─────────────────────────────────────────────────────────────┘
```

#### Архитектура серверной части (Backend)

Серверная часть спроектирована с использованием **модульной архитектуры** NestJS. Каждый функциональный блок представляет собой отдельный модуль, что обеспечивает:
- **Высокую модульность**: Каждый модуль отвечает за одну область (Auth, Events, Users и т.д.)
- **Легкость тестирования**: Модули могут тестироваться изолированно
- **Возможность масштабирования**: Новые модули добавляются без изменения существующего кода

##### Структура модуля (на примере Events Module):

```
events/
├── events.controller.ts       # Endpoints: GET /events, POST /events/:id, etc.
├── events.service.ts          # Бизнес-логика: создание, редактирование событий
```

**Guards (Стражи доступа):**
Проверяют JWT-токен и роли пользователя перед выполнением метода.

```typescript
@Injectable()
export class RolesGuard implements CanActivate {
  constructor(private reflector: Reflector) {}

  canActivate(context: ExecutionContext): boolean {
    const requiredRoles = this.reflector.get<Role[]>('roles', context.getHandler());
    const request = context.switchToHttp().getRequest();
    const user = request.user;

    return requiredRoles.some(role => user.role === role);
  }
}
```

#### Взаимодействие с базой данных (ORM - Prisma)

Prisma ORM используется для типобезопасного взаимодействия с PostgreSQL.

**Преимущества Prisma:**
1. **Типобезопасность**: TypeScript автоматически подсказывает доступные поля и методы
2. **Автоматические миграции**: Изменения в schema.prisma автоматически применяются к БД
3. **Query builder**: Интуитивный API для построения сложных запросов
4. **Отсутствие N+1 проблемы**: Встроенный механизм для загрузки связанных данных

```prisma
model Event {

  description     String    @db.Text

  location        String
  capacity        Int
  registrations   EventRegistration[]
  curator         User      @relation(fields: [curatorId], references: [id])
  curatorId       String
  category        String

  id              String    @id @default(cuid())
```

### 1.4 Безопасность данных и конфиденциальность

Обеспечение безопасности и конфиденциальности данных является критическим аспектом, особенно при работе с персональной информацией студентов.

#### Аутентификация и авторизация

**JWT (JSON Web Token):**
- При входе пользователя сервер генерирует зашифрованный JWT-токен с информацией о пользователе
- Токен отправляется клиенту и сохраняется в localStorage
- При каждом запросе токен приправляется в заголовке Authorization
- Сервер проверяет подпись токена и извлекает данные пользователя

```
POST /auth/login
Request: { email: "user@bgitu.ru", password: "123456" }
Response: { 
  access_token: "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9..."
}

GET /events
Headers: {
  Authorization: "Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9..."
}
```

**Интеграция VKontakte OAuth 2.0:**
- Студент может авторизоваться через свой ВКонтакте
- Пароль никогда не передается серверу БГИТУ
- Токен VK используется для отправки уведомлений в личные сообщения

#### Защита от основных типов атак

| Тип атаки | Защита | Реализация |
|-----------|--------|-----------|
| SQL-инъекция | Параметризованные запросы | Prisma ORM автоматически параметризует все запросы |
| XSS (Cross-Site Scripting) | Экранирование данных | React автоматически экранирует пользовательский контент |
| CSRF (Cross-Site Request Forgery) | CSRF-токены | Использование SameSite cookies |
| Brute-force атаки | Rate limiting | Ограничение попыток входа до 5 в минуту с одного IP |
| Утечка данных | HTTPS/TLS | Все соединение между клиентом и сервером шифруется |

#### Хеширование паролей

Пароли хранятся в виде криптографических хешей, а не в открытом виде. Используется алгоритм **bcrypt** с адаптивным фактором сложности:

```typescript
async hashPassword(password: string): Promise<string> {
  const saltRounds = 10;
  return bcrypt.hash(password, saltRounds);
}

async comparePasswords(password: string, hash: string): Promise<boolean> {
  return bcrypt.compare(password, hash);
}
```

#### Ролевая модель доступа (RBAC)

Каждый маршрут API защищен проверкой роли пользователя:

```typescript
@Post()
@UseGuards(JwtAuthGuard, RolesGuard)
@Roles(Role.ADMIN, Role.CURATOR)
create(@Body() createEventDto: CreateEventDto) {
  return this.eventsService.create(createEventDto);
}
```

#### Аудит системы (модуль логирования)

Каждое значимое действие логируется:

```
2024-01-15 14:32:15 | USER_LOGIN | user_id=123 | email=student@bgitu.ru
2024-01-15 14:35:42 | EVENT_CREATED | event_id=456 | title="Конференция"
2024-01-15 15:10:18 | EVENT_REGISTRATION | user_id=789 | event_id=456
2024-01-15 15:45:30 | EVENT_UPDATED | event_id=456 | curator_id=123 | field_changed=location
```

#### Конфиденциальность персональных данных

- Персональные данные студентов защищены в соответствии с ФЗ-152 «О персональных данных»
- Доступ к email студентов имеют только администраторы и кураторы
- Телефоны не хранятся в системе
- История посещений событий доступна только студенту, кураторам его группы и администраторам
